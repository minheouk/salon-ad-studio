# src/pipelines/serving/mock (목업 API)

진짜 모델 대신 **정해진 형식의 가짜 결과를 돌려주는 API**입니다.
모델이 완성되기 전에도 서비스 개발이 화면을 만들고 연결해 볼 수 있게 합니다.

- 결과 이미지는 단색 PNG(1024×1024), 광고 문구는 `[목업] 광고 문구 N`입니다.
- 실제 모델은 이미지는 **GPT Image 2**, 광고 문구는 **GPT6 LUNA**를 쓸 예정입니다. 목업은 모델을 호출하지 않으므로 API 비용이 들지 않습니다.
- 받은 사진과 요청 내용은 메모리에서만 쓰고 **디스크에 저장하지 않습니다.** 회원 정보는 백엔드에서 관리합니다.
- Python 표준 라이브러리만 씁니다. 따로 설치할 패키지가 없습니다.

## 실행하기

저장소 루트에서 실행합니다. `--port`에는 [VM 가이드](../../../../docs/vm_member_guide.md)에 있는 **본인 API 포트**(`800N`)를 넣습니다.

```sh
python -m src.pipelines.serving.mock.server --port 8004
```

- 서버는 `127.0.0.1`에서만 받습니다. **외부에 포트를 열지 않습니다.** VM에서 띄웠다면 SSH 포트 전달로 내 PC에서 접속합니다.
- 종료는 실행한 터미널에서 `Ctrl+C`를 누릅니다. 작업과 결과는 메모리에만 있어서 서버를 끄면 모두 사라집니다.

## 전체 흐름

생성은 시간이 걸리므로 **작업(job)을 등록하고, 상태를 조회해서 끝나면 결과를 받는** 방식입니다.

```
1. POST /api/jobs/generate        → 202, job_id, status: processing
2. GET  /api/jobs/{job_id}         → 1~2초 간격으로 조회
3. status: succeeded               → results[].url 로 이미지 다운로드
   status: failed / timeout        → POST /api/jobs/{job_id}/retry 로 재시도 (5번까지)
   사용자가 취소                     → POST /api/jobs/{job_id}/cancel
```

- 작업은 **한 번에 하나씩 순서대로** 처리합니다.
- 목업은 화면에서 "처리 중" 상태를 볼 수 있도록 작업 하나에 **3초**가 걸리게 해 두었습니다.

## 작업 등록

### `POST /api/jobs/generate`: 사진으로 광고 만들기

헤더에 **`Idempotency-Key`가 반드시 있어야 합니다.** 사용자가 버튼을 한 번 누를 때마다 새 값(예: UUID)을 만들어 보냅니다.

```http
POST /api/jobs/generate
Content-Type: application/json
Idempotency-Key: 6f1c2b0e-...

{"photos": ["data:image/jpeg;base64,..."], "prompt": "봄 시즌 펌 할인 광고"}
```

| 필드 | 규칙 |
|---|---|
| `photos` | 1~5장, PNG 또는 JPG, 한 장당 10MB 이하 (data URL) |
| `prompt` | 비어 있으면 안 됨, 100자 이하 |

결과는 광고 **5개**입니다.

### `POST /api/jobs/edit`: 챗봇으로 수정하기

```json
{"image": "data:image/png;base64,... (직전 결과)", "prompt": "배경을 밝은 파란색으로 바꿔 주세요"}
```

`image`와 `prompt`는 위와 같은 규칙으로 검사합니다. 결과는 광고 **1개**입니다.

### 중복 요청 (Idempotency-Key)

| 상황 | 응답 |
|---|---|
| 처음 보는 키 | `202`, 새 작업 |
| 같은 키, 같은 내용 (네트워크 오류 후 다시 보냄 등) | `200`, **처음 만든 작업을 그대로** 돌려줌. 새로 만들지 않음 |
| 같은 키, 다른 내용 | `409 IDEMPOTENCY_CONFLICT` |

## 작업 상태 조회: `GET /api/jobs/{job_id}`

```json
{
  "job_id": "3f2a...",
  "type": "generate",
  "status": "succeeded",
  "retries": 0,
  "timing_ms": {"wait": 2, "run": 3001, "total": 3003},
  "results": [
    {"url": "/api/results/3f2a.../1?expires=...&signature=...", "copy": "[목업] 광고 문구 1"}
  ],
  "results_expire_in_seconds": 86399
}
```

### 상태

화면에는 **처리 중 / 완료 / 실패** 3단계로 보여 주면 됩니다.

| `status` | 화면 표시 | 끝난 상태인가 | 다음 행동 |
|---|---|---|---|
| `processing` | 처리 중 | 아니요 (대기 중 포함) | 계속 조회, 취소 가능 |
| `succeeded` | 완료 | 예 | `results`로 다운로드 |
| `failed` | 실패 | 예 | `error.message` 표시, 재시도 가능 |
| `timeout` | 실패 | 예 | `error.message` 표시, 재시도 가능 |
| `canceled` | 실패 (취소됨) | 예 | 새로 요청 |

- `failed`와 `timeout`이면 `error: {"code", "message"}`가 함께 옵니다.

### 실패·시간 초과 화면 시험하기

목업은 모델을 부르지 않아서 보통은 항상 `succeeded`로 끝납니다.
화면에서 실패 화면을 확인하려면, `prompt`에 아래 표시를 넣으면 됩니다. `generate`와 `edit` 모두 됩니다.

| `prompt`에 넣을 표시 | 끝나는 상태 | `error` |
|---|---|---|
| `[mock:failed]` | `failed` | `{"code": "GENERATION_FAILED", "message": "광고를 만들지 못했습니다. 다시 시도해 주세요."}` |
| `[mock:timeout]` | `timeout` | `{"code": "TIMEOUT", "message": "처리 시간이 60초를 넘었습니다. 다시 시도해 주세요."}` |

예: `"prompt": "봄 시즌 펌 할인 광고 [mock:failed]"`

- 60초를 기다리지 않도록, 다른 작업처럼 **3초 뒤에** 그 상태로 끝납니다.
- 재시도해도 같은 표시가 남아 있어서 계속 같은 상태로 끝납니다. 그래서 재시도 5번 제한(`RETRY_LIMIT`) 화면도 시험할 수 있습니다.
- 표시도 100자 제한에 포함됩니다.
- **목업 전용 기능입니다.** 실제 서빙 API에는 넣지 않습니다.

### 처리 시간 (`timing_ms`)

| 항목 | 범위 |
|---|---|
| `wait` | 등록부터 처리 시작까지 (앞 작업을 기다린 시간) |
| `run` | 처리 시작부터 끝까지 (실제 API에서는 모델 추론 시간) |
| `total` | 등록부터 끝까지 = `wait` + `run` |

- 서버가 요청 본문을 다 받은 뒤부터 잽니다. 업로드·다운로드 같은 **네트워크 시간은 들어가지 않습니다.** 사용자가 체감하는 전체 시간은 화면에서 재면 됩니다.
- 끝나지 않은 작업은 지금까지 걸린 시간을 보여 주고, 아직 시작하지 않은 단계는 `null`입니다.

## 시간 초과

| 구분 | 상한 | 기준 |
|---|---|---|
| 서버 | **60초** | 작업 **등록 시점**부터. 앞 작업을 기다린 시간도 포함합니다. 넘으면 `timeout`으로 끝냅니다 |
| 웹 호출 | **70초** | 화면이 처음 요청한 시점부터. 이때까지 끝난 상태를 못 받으면 화면에서 포기합니다 |

서버 상한(60초)이 웹 제한(70초)보다 짧기 때문에, 화면은 포기하기 전에 항상 끝난 상태를 받을 수 있습니다.

## 취소와 재시도

| 요청 | 조건 | 실패 응답 |
|---|---|---|
| `POST /api/jobs/{id}/cancel` | `processing`일 때만 | `409 JOB_FINISHED` |
| `POST /api/jobs/{id}/retry` | `failed` 또는 `timeout`일 때만 | `409 NOT_RETRYABLE` |
| | 재시도는 작업당 **5번까지** | `409 RETRY_LIMIT` |

- 재시도는 같은 `job_id`로 다시 처리합니다. `retries`가 1씩 늘고, 60초 상한도 재시도한 시점부터 다시 셉니다.
- 둘 다 성공하면 `202`와 바뀐 작업 상태를 돌려줍니다.

## 동시 요청

- 작업은 한 번에 하나만 처리하고, 나머지는 순서대로 기다립니다.
- **처리 중 1개 + 대기 2개**, 모두 3개까지 받습니다. 그 이상이면 새 요청을 거절합니다.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 10

{"code": "QUEUE_FULL", "message": "지금 처리 중인 요청이 많습니다. 잠시 후 다시 시도해 주세요."}
```

대기를 길게 두지 않은 이유는, 순차 처리에서 앞에 작업이 많이 쌓이면 서버 상한 60초 안에 끝나기 어렵기 때문입니다.

## 결과 받기와 보관

- 결과는 **`succeeded`가 된 시점부터** 받을 수 있습니다. 그 전에는 `results`가 없습니다.
- `results[].url`은 **서명 URL**입니다. `GET`으로 받으면 PNG 파일이 옵니다. 서버 주소 뒤에 붙여서 씁니다.
  - 개인정보 보호를 위해 **공개 URL은 쓰지 않습니다.** 외부 저장소(S3 등)에 올리지 않고, 결과는 이 서버 안에만 있습니다.
  - 이 주소는 서버 안의 경로라서, `127.0.0.1` 서버에 연결된 쪽(SSH 포트 전달, VM 안의 백엔드)에서만 열립니다.
  - **1시간 동안만 유효합니다.** 만료되면 `403 URL_EXPIRED`가 옵니다. 작업 상태를 다시 조회하면 새 주소를 받을 수 있습니다.
  - 주소를 고치면 `403 INVALID_SIGNATURE`가 옵니다.
- 서버는 끝난 작업과 결과를 **끝난 시점부터 24시간** 보관합니다. `results_expire_in_seconds`가 남은 시간입니다. 지나면 작업이 지워져서 `404 JOB_NOT_FOUND`가 옵니다.
- 서명 키는 서버를 켤 때마다 새로 만들기 때문에, 서버를 다시 켜면 이전 주소는 모두 무효가 됩니다.

## 실패 응답

실패하면 HTTP 상태 번호와 함께 `code`, `message`를 돌려줍니다.
- 화면에서는 **HTTP 상태 번호로 입력 오류(4xx)인지 판단**하고, `code`로 분기합니다.
- `message`는 사용자에게 그대로 보여 주면 됩니다.

```json
{"code": "EMPTY_PROMPT", "message": "요청 내용을 입력해 주세요."}
```

**입력 오류**: 작업을 만들기 전에 거절합니다.

| HTTP | `code` | 언제 |
|---|---|---|
| 400 | `MISSING_IDEMPOTENCY_KEY` | `Idempotency-Key` 헤더가 없음 |
| 400 | `EMPTY_PROMPT` | 요청 내용이 비었거나 공백만 있음 |
| 400 | `PROMPT_TOO_LONG` | 요청 내용이 100자를 넘음 |
| 400 | `PHOTO_COUNT` | 사진이 0장이거나 5장을 넘음 |
| 400 | `UNSUPPORTED_FORMAT` | PNG·JPG가 아님 |
| 400 | `FILE_TOO_LARGE` | 사진 한 장이 10MB를 넘음 |
| 400 | `BROKEN_IMAGE` | 파일이 손상됨 (아래 참고) |
| 400 | `RESOLUTION_TOO_LOW` | 짧은 변이 512px 미만 |
| 400 | `RESOLUTION_TOO_HIGH` | 긴 변이 8192px 초과 |
| 400 | `INVALID_JSON` | 본문이 JSON 객체가 아님 |
| 413 | `BODY_TOO_LARGE` | 요청 전체가 약 68MB(10MB × 5장을 base64로 감싼 크기)를 넘음 |
| 415 | `INVALID_JSON` | `Content-Type`이 `application/json`이 아님 |

여러 장 중 하나가 문제면 `message`에 몇 번째 사진인지 적어 줍니다. 예: `2번째 사진 파일이 손상되었습니다.`

**작업·결과 관련 오류**

| HTTP | `code` | 언제 |
|---|---|---|
| 409 | `IDEMPOTENCY_CONFLICT` | 같은 키로 다른 내용을 보냄 |
| 429 | `QUEUE_FULL` | 처리 중·대기 중 작업이 가득 참 (`Retry-After` 헤더 포함) |
| 409 | `JOB_FINISHED` | 이미 끝난 작업을 취소함 |
| 409 | `NOT_RETRYABLE` | `failed`·`timeout`이 아닌 작업을 재시도함 |
| 409 | `RETRY_LIMIT` | 재시도 5번을 넘음 |
| 403 | `INVALID_SIGNATURE` | 다운로드 주소가 올바르지 않음 |
| 403 | `URL_EXPIRED` | 다운로드 주소의 1시간이 지남 |
| 404 | `JOB_NOT_FOUND` | 없는 작업이거나 24시간 보관이 끝남 |
| 404 | `RESULT_NOT_FOUND` | 없는 결과 번호 |
| 404 | `NOT_FOUND` | 없는 주소 |

## 손상된 파일과 해상도 처리

이미지 라이브러리 없이 **파일 구조만 읽어서** 검사합니다.

- **형식은 파일 내용으로 판별합니다.** 확장자나 data URL의 형식 표기는 믿지 않습니다. 예를 들어 이름만 `.jpg`인 다른 파일은 `BROKEN_IMAGE`가 됩니다.
- **PNG**: 모든 청크의 CRC(검사값)를 확인하고, 끝 표시(`IEND`)까지 있어야 통과합니다. 업로드 중 잘린 파일이나 중간이 깨진 파일이 여기서 걸립니다.
- **JPG**: 끝 표시(`EOI`)가 있어야 하고, 본문 전에 해상도 정보(`SOF`)가 있어야 통과합니다.
- **해상도 기준**
  - **최소: 짧은 변 512px.** 이보다 작으면 광고 이미지로 쓰기에 화질이 부족합니다.
  - **최대: 긴 변 8192px.** 일반 휴대폰 사진(12MP, 4032×3024)은 통과합니다. 48MP 이상의 고해상도 원본만 막습니다.
- **한계**: 구조 검사라서 화소 데이터 안쪽이 깨진 경우까지는 잡지 못합니다. 실제 서빙 API에서는 이미지를 열어 보는 디코딩 검사를 더하고, 최대 해상도 이하의 큰 사진은 거절하지 않고 모델 입력 크기로 줄이는 방식을 권장합니다.

## 정해지지 않은 것

- **요청 전체 최대 용량**: 지금은 장당 10MB × 5장을 기준으로 임시로 정했습니다.
- **입력 사진 수에 따른 결과 수**: 지금은 사진 수와 관계없이 `generate` 결과를 5개로 고정했습니다.
- **대기 가능한 작업 수**: 처리 중 1개와 대기 2개는 임시로 정한 값입니다.
- **결과 파일 저장 위치**: 목업은 메모리에 둡니다. 실제 서버는 24시간 보관할 곳(`outputs/` 등, 커밋 금지)을 정해야 합니다.
- **5초 동영상**: 지원 여부가 정해지면 추가합니다.
- **이 요청·응답 형식은 아직 서빙 쪽 제안입니다.** 서비스·모델 담당과 합의하면 `src/common/`에 정의합니다. `src/common/`은 공용 파일이라 PM 승인이 필요합니다.
